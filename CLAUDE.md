## What is mktba

**mktba** — open-source исламская wiki-платформа, hard fork WikiWeaver. Контент организован как иерархическое дерево статей, каждая содержит параграфы, а каждый параграф — одно или несколько «мнений» (Opinion), привязанных к одной или нескольким школам исламского права (мазхабам). Поддерживаются 4 канонические суннитские школы (Hanafi, Maliki, Shafi'i, Hanbali) плюс произвольные кастомные школы per-article. Админ-панель (`/admin`, доступна только по прямому URL) управляет всем контентом.

UI — только на русском. Целевой домен — `mktba.ru`.

## Commands

### Backend (run from repo root)
```bash
docker compose up -d postgres
dotnet build Mktba.sln            # plain `dotnet build` fails with MSB1011 (docker-compose.dcproj)
```

## Architecture

Clean DDD layering — each layer depends only on layers below it:

```
Mktba.Domain          → pure entities, no external dependencies
Mktba.Application     → services, DTOs, AutoMapper profiles
Mktba.Infrastructure  → EF Core (PostgreSQL), repositories, Unit of Work, seeders
Mktba.Api      → ASP.NET Core 8 Minimal API, JWT auth, CORS, Swagger
mktba.react           → React 19 + TypeScript, React Router v7 framework mode (SSR), React Query v5, Tailwind CSS v4, Vite
```

**Key domain concepts:**
- `Article` contains ordered `Paragraph`s (slot).
- `Article.Slug` — URL segment (`/article/{slug}`), transliterated from the title or set by hand; unique per `Locale` together with old slugs (index `(Locale, Slug)` on both tables). A changed slug leaves an `ArticleSlugRedirect` (carrying the article's locale); old `/article/{id}` links redirect to the slug URL. Transliteration lives in `ArticleSlugRules` (C#), the `AddArticleSlugs` migration backfill (SQL) and `src/shared/slug.ts` (editor prefill) — keep the three identical. User profile slugs reuse the same two functions with the fallback word `author`.
- `Article.Locale` / `TranslationGroupId` (M-09, #27) — D6: a translation is a separate article per language. `Locale` is a short code from `Locales.Supported` (`Mktba.Domain/Entities/Locales.cs`, the one list; default `ru`, anything else → `locale_unsupported`), set on create and never changed. Articles sharing a `TranslationGroupId` are translations of each other, at most one per locale (unique index); a new article starts its own group. `GET /articles/by-slug/{slug}/content?locale=` defaults to `ru`. Revision snapshots do not carry the locale (it cannot change). School names: `School.Name`/`ShortName` are Russian, other languages live in `SchoolTranslation(SchoolId, Locale, Name, ShortName)` (system schools seeded with `en`; not exposed in the API yet, I-07 #111). Tags are a per-article string list, so they are already per language. English UI/routes are Stage 5 (epic 9).
- Each `Paragraph` holds one or more `Opinion`s; one `Opinion` is marked default (fallback when user's mazhab has no specific opinion).
- `Opinion` ↔ `School` is M:N through `OpinionSchool` join.
- A plain paragraph (exactly one `Opinion`) is common to all schools and has no school links: every write path (`/paragraph`, `/articles/content`, `/articles/{id}/content`) rejects school ids on it with `paragraph_plain_schools_not_allowed`, and the editor offers school selection only in a block with two or more opinions (a block left with one non-empty opinion is saved as a plain paragraph, without school ids). School links belong to versioned paragraphs (two or more opinions).
- `School` — 4 канонические (`IsSystem=true`) + кастомные per-article (`ArticleScopeId` nullable FK).
- `Source` / `OpinionSource` (M-07, #71): a `Source` is an entry of one shared directory — `Kind` (`Book`, `HadithCollection`, `Quran`, `Other`; stored by name), `Title` (≤ 300), optional `Author` (≤ 200), `Details` (≤ 500, free-form publication data) and `Url` (absolute http(s), ≤ 2048). It holds what every citation shares; the place inside the work (page, hadith number, sura:ayah) is the citation's `Locator` (≤ 200, optional). An `OpinionSource` (`OpinionId`, `SourceId`, `Order`, `Locator`) is one citation of an opinion; an opinion may cite one source several times. Any opinion may cite, a plain paragraph's included (sources are not tied to schools). Citations travel on the content DTOs as `opinions[].sources: [{ sourceId, locator }]` (list order = order, full replace like the rest; every write path, `/paragraph` too) and the read-only `ArticleContentDto.sources` lists each cited entry once, in the order of first citation. An unknown id is rejected (`source_not_found`), not dropped. A cited entry cannot be deleted (`source_in_use`, FK `Restrict`); citations go with their opinion (cascade). A second entry of the same kind, title and author (ignoring case) is refused with `source_duplicate` — a check in `SourceService`, not a database constraint. Entries are not versioned and not localized (one title as typed), and are not in the full-text search (`SearchVector` is unchanged). Authors and admins read and add entries (`CanEditArticles`); only admins edit or delete one (`CanEditAnyArticle`), because an edit shows in every article citing it. Rules live in `OpinionCitations` and `SourceService`; error codes `source_*`.
- `Article.Status` (`ArticleStatus`): `Draft → InReview → Published → Archived`. Allowed moves live only in `ArticleStatusTransitions` (Draft→InReview, InReview→Published/Draft, Published→Archived, Archived→Draft), changed via admin-only `POST /articles/{id}/status`. New articles are `Draft`.
- Anonymous readers see only `Published` (`ArticleVisibility`): non-Published articles answer 404, related links to them are dropped, and the public tree hides a non-Published article together with its subtree. Admins see every status (badge in the tree, status panel in the editor).
- `Article` dates and authorship (M-03): `CreatedAt`, `UpdatedAt` (any content/metadata/authorship save; not status changes), `PublishedAt` (first move to Published; kept through archiving and re-publishing) — UTC, set through the injected `TimeProvider`. `AuthorId` = creating user (nullable, SetNull on user delete); co-authors via `ArticleCoAuthor` (ArticleId, UserId), never the author; admin API `GET/PUT /articles/{id}/authors`, users list `GET /users`. Readers get the dates and, on the content reads (`GET /articles/{id}/content` and by slug), a read-only `authors` list (P-06, #94): the author first, then the co-authors by user id, each `{ displayName, slug }` — no id, no email. Only users with a display name are listed (nobody named → an empty list), and `slug` is set only when the author page answers (the user is credited on a Published article), so an admin previewing a draft whose author has nothing published gets the name without a link target. It is null in the answer to a save and is not in revision snapshots. Emails stay admin-only.
- `ArticleRevision` (M-04): append-only history. Every save through `POST /articles/content` / `PUT /articles/{id}/content` writes, in the same transaction, revision N+1 (`Number` per article, `AuthorId`, optional `Comment` from the DTO's write-only `editComment`, `Snapshot` = jsonb of `ArticleSnapshotDto` — `schemaVersion` 3, self-contained: title/slug/summary/tags/infobox/paragraphs/opinions/school ids/related links with title+slug at save time, SEO fields; version 1 has no `seo` and stays readable — restoring it clears the SEO overrides; version 3 adds each opinion's citations with a copy of the source entry as it was — kind, title, author, details, url — so versions 1–2 have none and a revision reads the same after the entry is edited or deleted; a restore re-links the citations by source id to the directory as it is now and leaves out those whose entry was deleted since). The current tables stay the working copy. Revisions are never updated or deleted; rollback (`POST /articles/{id}/revisions/{n}/restore`) saves the old snapshot as a new revision. Admin API: `GET /articles/{id}/revisions`, `/revisions/{n}`, `/revisions/compare?from=&to=`; diff is rendered client-side (`pages/article-history/revisionDiff.ts`), UI at `/admin/articles/{id}/history`. The `AddArticleRevisions` migration backfills revision 1 for existing articles in SQL — keep its JSON shape in step with `ArticleSnapshotDto`. `Article.PublishedRevisionId` is set to the latest revision on every move to Published: the hook for D4 (#20), readers are still served the working copy. Paragraph endpoints, `POST/PUT /articles` metadata and authorship changes do not write revisions.
- Article SEO fields (M-10, #28): `SeoTitle` (≤ 70), `SeoDescription` (≤ 160), `SocialImageUrl` (absolute http(s) URL or site-relative `/path`, ≤ 2048; no upload), `NoIndex` — written as `seo` on the content DTOs (full replace like the other fields: `seo: null` clears them), validated in `ArticleSeo` (codes `article_seo_title_too_long`, `article_seo_description_too_long`, `article_social_image_url_invalid`; client mirror `src/shared/seo.ts`). Read-only `meta` on `ArticleContentDto` carries the effective values: title = SeoTitle ?? Title; description = SeoDescription ?? Summary ?? plain text of the first paragraph's default opinion cut to 160 chars on a word boundary (null if none). The article page renders `<title>`, description, Open Graph, canonical (`/article/{slug}`) and robots noindex through React 19 document metadata (`components/article/ArticleMeta.tsx`) — a client-side stopgap until SSR (O-01 #52, O-04 #55).
- Search (R-10, #46): PostgreSQL full-text search, `russian` configuration. The index lives only in the database (migration `AddArticleSearch`), not in the EF model: stored generated `tsvector` columns `"Articles"."SearchVector"` (title weight A; summary and tags B) and `"Opinions"."SearchVector"` (opinion text D, Markdown/HTML reduced to text by the SQL function `mktba_search_plain_text`), a GIN index on each, the aggregate `mktba_tsvector_agg`; ё is folded to е in the vectors and the query. PostgreSQL keeps the columns current on every write path, so no code maintains the index — but changing what is indexed means a migration that re-creates the generated column. `ArticleSearchRepository` (raw SQL, PostgreSQL only) finds candidates by any query word through the indexes, then requires every word (`plainto_tsquery`, operators in the query are just text) in the article's vectors put together, so words may be spread over the title and several opinions; ranking is `ts_rank`. Results are the same for every caller: Published with every ancestor Published (a recursive CTE, the navigation tree's rule), one `locale`. Highlighting is `ts_headline` with private-use marker characters that `ArticleSearchService.ParseSegments` turns into `{ text, match }` runs — the API never returns markup and the UI renders the runs as text (`<mark>`). Limits: query 2–200 characters (`search_query_too_short` / `search_query_too_long`), `pageSize` ≤ 50, `page` ≤ 100. Tests that need PostgreSQL use `PostgresDatabaseFixture` (Mktba.Application.Tests; server from `MKTBA_TEST_DB_CONNECTION`, default the compose `postgres`); the InMemory API tests cannot run the search itself.
- `NavigationTree` exposes the article hierarchy for the sidebar.
- `User` (ex-`AdminUser`) authenticates via JWT; `Role` is `Reader`/`Author`/`Scholar`/`Admin` (stored by name, read from the DB on every request). Endpoints name a policy from `Mktba.Api/Infrastructure/Policies.cs`, never a role; `EndpointAuthorizationMatrixTests` lists every endpoint's policy. The first user is `Admin`; everyone else registers with an `Invite` (U-04 #32): a DB row with the SHA-256 hash of a random token (raw token shown once), a `Role`, `ExpiresAtUtc` (default `Auth:InviteTokenLifetimeHours`, max 720 h), optional `Note`, single-use — `UsedAtUtc`/`RevokedAtUtc` are EF concurrency tokens, so the use is a conditional update in the same SaveChanges as the new user and a racing second use fails with `invite_used`. Admins change roles via `PUT /users/{id}/role`; the last admin cannot be demoted (`last_admin_demotion`). Per-object rights for authors: U-02 #30. Frontend mirror: `src/auth/roleAccess.ts`, `useCurrentUser` (`GET /auth/me`).
- User profile (U-07, #72): nullable columns on `User` — `DisplayName` (one line, ≤ 100), `Slug` (≤ 80, unique index), `AvatarUrl` (validated like `SocialImageUrl`; no upload until U-08 #73), `Bio` (plain text, ≤ 1000), `Degree` (≤ 150), `Institution` (≤ 200) — plus `UserLink(UserId, Order, Label ≤ 60, Url)`: at most 5 labelled absolute http(s) links. Every field is optional and existing users start empty; rules in `UserProfileRules` (codes `profile_*`), client mirror `src/shared/profile.ts`. A user without a display name is shown nowhere in public — nothing falls back to the email. The slug follows `ArticleSlugRules` (same transliteration and shape, fallback word `author`): it exists exactly when the name does, a blank slug on save keeps the current one or is derived from the name the first time (`name`, `name-2`, …), and a changed slug is **not** kept — no redirects, the old address answers 404. `Degree`/`Institution` are self-declared, stored for any role and given to readers only while the role is `Scholar`; a confirmed degree belongs to the verification epic (V-01 #117, V-02 #118). A profile is public (`GET /authors/{slug}`, `PublicProfileDto`: no id, no email) only when the user has a display name **and** is the author or a co-author of at least one Published article; otherwise 404 `author_not_found`, so the endpoint cannot list accounts. `UserProfileDto.isPublic` tells the owner which it is. Links are the user's own text: render them with `rel="nofollow noopener"`, the bio as plain text. UI: `/admin/profile` («Мой профиль», any signed-in role) — the minimal form; the public author page is P-01 #89, the author line on the article P-06 #94, notification settings and the rest of profile editing P-05 #93.
- `FeedbackMessage` (F-02, #67): one anonymous message — `Type` (`ArticleError`/`SiteProblem`/`Idea`, stored by name, values start at 1), `Text` (≤ 4000), optional `Contact` (≤ 200), `PageUrl` (absolute http(s) or site-relative, ≤ 2048), `ArticleId` (SetNull on article delete), `Mazhab` (system school slug), `CreatedAtUtc`. The row is also the delivery queue: `DeliveryState` (`Pending` → `Delivered` | `Failed`), `Attempts` (EF concurrency token: an attempt starts by incrementing it, so two workers cannot take one row), `NextAttemptAtUtc`, `LastAttemptAtUtc`, `LastError` (status code and GitHub's message, never a key or token), `DeliveredAtUtc`, `GitHubIssueNumber`/`GitHubIssueUrl`, `DeliveryKey` (random guid, the hidden `<!-- mktba-feedback:… -->` marker in the issue body). `FeedbackService` validates and stores (control characters and unpaired surrogates are stripped; an unknown article id or mazhab is dropped, not an error); `FeedbackDeliveryWorker` (hosted service in `Mktba.Api/Infrastructure`, every `Feedback:Delivery:PollIntervalSeconds`) runs `FeedbackDeliveryService`, which files the issue through `IFeedbackIssueTracker` = `GitHubIssueClient` (GitHub App: RS256 JWT from the private key → installation of the repository → installation token cached until 5 min before expiry → `POST /repos/{owner}/{repo}/issues` with labels `feedback`, `needs-triage`). Decision D9 (#37): the issue (format in `FeedbackIssueFormatter`) carries type, text, page, the article title only if Published, the mazhab name and «контакт оставлен / не оставлен» with the message number — never the contact; IP and User-Agent are not stored at all. Failures: anything that is not about the message (network, 5xx, 429, 401/403/404/410, unreadable key, a 422 naming `labels`) leaves it `Pending` with a doubling delay (`RetryBaseSeconds` … `RetryMaxSeconds`), no attempt limit, and ends the run; a 422 on the issue itself → `Failed`. From the second attempt on the repository's issues changed since the message arrived (at most 300) are searched for the marker first, so an attempt cut off after GitHub created the issue does not create a second one. Not configured (`Feedback:GitHub`: `Enabled`, `AppId`, `Owner`, `Repository` and `PrivateKeyPath` or `PrivateKey`; the committed settings have no key) → the worker does not start and messages stay `Pending` with zero attempts; they are delivered once the app is configured. Tests never reach GitHub: `MktbaApiFactory` replaces the tracker, the e2e API runs with `Feedback__GitHub__Enabled=false`. Not there yet: the form (F-01 #66), the admin list (F-04 #163).
- Feedback protection (F-03, #68). Intake: `RateLimiting:Feedback` (5 / 600 s per client IP → 429 `too_many_requests`); `Feedback:Intake:MaxPerHour` (30; 0 = off) caps stored messages from everyone in any 60 minutes → 429 `feedback_limit_reached` (`TooManyRequestsException`, `Retry-After`), counted from the table itself (the N-th newest row by id), so it survives restarts and is not used up by trapped or invalid requests. Trap field `website` on `FeedbackCreateDto`: anything but white space → `FeedbackService` answers 202 with the next free number before any validation and stores nothing (one log line, no details); the form (#66) must render it hidden (`tabindex="-1"`, `autocomplete="off"`, `aria-hidden`, CSS) and send it as is. `Feedback:SiteUrl` (empty by default): when set, an absolute `pageUrl` on another origin is dropped, the message kept; site-relative paths always pass. The IP only keys the limiter's in-memory window — never stored, never logged with a message (D9). Issue body (`FeedbackIssueFormatter`, the only place visitor text becomes Markdown): the text is a fenced code block with a fence longer than any backtick run in it, `pageUrl` / article title / mazhab name are code spans built the same way, so nothing a visitor writes is parsed (no mentions, `#123` / `owner/repo#1` / SHA / issue-URL cross-links, images, links, HTML, headings) and it cannot leave the block or forge the marker; bidi overrides and isolates are stripped; `EndsWithMarker` — the marker counts only as the last line of an issue (`GitHubIssueClient.FindByMarkerAsync`). Any new visitor-controlled field must go through `CodeSpan`/`CodeBlock`. The issue title carries the published article's title as is (authors' text, not the visitor's). Client IP behind a proxy: `ForwardedHeaders:KnownProxies` / `KnownNetworks` / `ForwardLimit` (`ForwardedHeadersSetup`, first in the pipeline; empty = `X-Forwarded-For` ignored, as before) — it serves every per-IP limit, not only feedback. Tests: `MktbaApiFactory` runs with generous feedback limits; `FeedbackProtectionEndpointTests` start their own API per test.

**API surface** (all in `Mktba.Api/Endpoints/`):
- `/auth` — `GET /status`, `POST /register` (first admin, then only with an invite token; the user gets the invite's role), `POST /login`, `POST /refresh`, `POST /logout`, `POST /logout-all`, `GET /sessions`, `DELETE /sessions/{id}`, `GET /me`
- `/invites` — `GET /`, `POST /` (role, lifetime, note → token once), `POST /{id}/revoke` (Admin only)
- `/users` — `GET /` (with roles and display names), `PUT /{id}/role`, `GET|PUT /{id}/profile` (Admin only)
- `/profile` — `GET /`, `PUT /` (the signed-in user's own profile, a full replace; any role)
- `/authors/{slug}` — the public profile; 404 unless the user has a display name and is credited on a Published article
- `/authors/{slug}/articles?locale=&page=&pageSize=` — the author's articles a reader can open (P-01, #89): written or co-authored, Published with every ancestor Published, no empty stubs, by `PublishedAt` newest first; `AuthorArticlesDto { total, page, pageSize, items }`, page size 20 by default and at most 50; the same 404 as the profile (`AuthorArticlesService`, sharing `ArticleReachability` with `RecentArticlesService`). The list may be empty for a public author: a profile is public by any Published article
- `/navigationTree/tree` — article hierarchy for the sidebar
- `/articles` — article CRUD (`GET /`, `GET /{id}`, `POST /`, `PUT /{id}`, `DELETE /{id}`)
- `/articles/{id}/content`, `POST /articles/content` — article with its paragraphs and opinions, read and saved as a whole
- `/articles/by-slug/{slug}/content` — the same content by slug; an old slug answers 302 to the current slug's URL
- `/articles/recent?locale=&limit=` — the home page's lists (R-05, #41): `new` by `PublishedAt`, `updated` = saved after publication, by `UpdatedAt`; public, the same for every caller: Published, every ancestor Published, no empty stubs (`RecentArticlesService`)
- `/search?q=&locale=&page=&pageSize=` — full-text search (R-10, #46), public; items carry `title` / `summary` / `snippet` as `{ text, match }` runs and the snippet's `paragraphId`
- `/paragraph` — paragraph CRUD (`GET /`, `GET /{id}`, `POST /`, `PUT /{id}`, `DELETE /{id}`)
- `/schools` — `GET /system`, `GET /article/{articleId}`, `POST /`, `DELETE /{id}`
- `/sources` — `GET /?q=&kind=&limit=` (the directory, for the editor's picker), `POST /` — authors and admins; `PUT /{id}`, `DELETE /{id}` (refused while cited) — admins
- `/feedback` — `POST /` (F-02, #67), public: `{ type, text, contact?, pageUrl?, articleId?, mazhab? }` → `202 { id }` once the message is stored; the GitHub issue is created in the background, so the answer does not depend on GitHub. Errors: `feedback_type_invalid`, `feedback_text_required`, `feedback_text_too_long`, `feedback_contact_too_long`, `feedback_page_url_invalid`; 429 `too_many_requests` (per client) and `feedback_limit_reached` (all visitors, per hour), both with `Retry-After`. Optional `website` is the trap field for bots (F-03, #68): filled in → 202 and nothing stored
- `/admin` — `POST /cleanup`, `GET|PUT|DELETE /ai-settings`, `POST /ai-style`, `POST /ai-check`

**Frontend rendering (O-01, decision D1):**
- React Router v7 framework mode, `appDirectory: 'src'`: `src/root.tsx` (document, providers), `src/routes.ts` (route config), `src/routes/*` (route modules), `src/entry.client.tsx` (browser startup: session restore, Metrika).
- Public routes have a server `loader` that fetches the API anonymously (`src/server/api.server.ts`, base `API_INTERNAL_URL`) into a server QueryClient and returns `dehydrate()`d state; the route component wraps the page in `HydrationBoundary`. A `clientLoader` skips the server on later client-side navigations (pages fetch through React Query as before). Loaders set status codes (`data(..., { status: 404 })`, `redirect(..., 301)`).
- `/admin/*` is client-only (`clientLoader.hydrate` + `HydrateFallback`); auth never runs on the server.
- Home page (R-05, #41): `src/pages/HomePage.tsx` — sections (top level of the navigation tree the public layout already loaded), new and updated articles (`GET /articles/recent`, prefetched by the home route's loader), the «что такое mktba» text, and the search field (`SearchForm`, leads to the results page). Not there yet: popular articles (needs view statistics, analytics epic).
- Search UI (R-10, #46): `/search?q=…&page=…` (`routes/search.tsx`, `pages/SearchPage.tsx`) — server-rendered from the query in the URL, owns its meta, `noindex` without a canonical (results pages are not for search engines; `robots.txt` does not block them, so the `noindex` is seen). URL and limits live in `src/shared/search.ts` (mirror of `ArticleSearchService`). `SearchForm` is a plain GET form that works before hydration. The public header's button and Ctrl+K / ⌘K (`components/search/searchShortcut.ts`: by physical key, left alone inside `textarea` / contenteditable) open `SearchDialog`; `MainLayout` ties the dialog to `location.key`, so any navigation closes it. The admin layout has no shortcut. The `WebSite` JSON-LD node names the search as a `SearchAction`. The sidebar's field is still only a filter of the tree. Not there: search analytics (N-06 #100), verification marks in results (V-08 #124).
- No `localStorage`/`window` during render: read stored values after hydration via `useHydrated()`; `useSession` renders anonymously on the server and while hydrating.
- Article header (R-06, #42): `ArticleBreadcrumbs` (home → ancestors from the public navigation tree via `findArticlePath` in `src/shared/articleTree.ts` → the article; shown for stubs and for an article the tree does not hold; the public tree already hides non-Published ancestors), the h1, then `ArticleDates` with the dates and the reading time. The reading time is computed on the client (`src/shared/readingTime.ts`, 180 words a minute) from each paragraph's default opinion, so the server HTML and the hydrated page agree whatever the reader's mazhab; a stub has none. The author line (P-06, #94) is the first item of `ArticleDates` — «Автор: …» / «Авторы: …, …» from the DTO's `authors`, a name linked (`rel="author"`) to `/authors/{slug}` only when it has a slug, no line when nobody is named; the article's JSON-LD `author` is then the `Person` node(s) of the authors with a page (same `@id` as on the author page), else the site `Organization`. `authorHref` lives in `src/shared/slug.ts` beside `articleHref` so the article bundle does not load `author.ts`. No verification widget (V-04 #120) yet.
- Article anchors and table of contents (R-07, #43): `buildArticleOutline` (`src/shared/articleOutline.ts`) is the one source of the ids — a paragraph is `p-{paragraph id}` (stable through edits and reordering), a heading is its transliterated text (`slugFromTitle`; repeats get `-2`, `-3` in reading order; `section` when nothing transliterates), never an id already taken on the page. Headings are parsed with the renderer's own syntax (`src/shared/markdownHeadings.ts`, which also holds the h2-nesting rule) and `MarkdownContent` puts the ids on them through `headingAnchors`. Only the opinion on screen gets heading ids (hidden panels have none), so the server HTML carries the default opinions' anchors and the reader's mazhab may change them after hydration; `useHashAnchor` re-aligns the page to the URL's `#anchor` then (also for `?mazhab=…#anchor` links and late fonts) until the reader touches the page. The right sidebar lists h2/h3 and highlights the current one (`useActiveSection`); it is hidden below `xl` (mobile: R-11 #47). `BackToTopButton` is client-only.
- Article footer (R-08, #44): `ArticleFooter` under the text, inside the article column — «В этом разделе» (the article's direct children in the public navigation tree; a stub is listed without a link, as in the tree and the breadcrumbs), «Связанные статьи» (`relatedLinks` of the content DTO; hidden from `xl` up, where the right sidebar already shows them) and previous / next (`findAdjacentArticles` in `src/shared/articleTree.ts`: the tree read top to bottom — a parent, its children, then the next sibling — stepping over stubs). Everything comes from data the page already has (the public tree hides non-Published articles, the API drops related links to them), so it is in the server HTML. A block with nothing to show is left out. The block headings are `h2` but are deliberately not in the table of contents: it lists the article's content, not its navigation. Last comes «Сообщить об ошибке» — always there, a link to the feedback form opened for this article (`errorReportHref`).
- Feedback form (F-01, #66): a page, `/feedback` (`routes/feedback.tsx`, `pages/FeedbackPage.tsx`), not a dialog — it has an address, is in the server HTML (`noindex`, no canonical), and its code is a route chunk of its own, outside the article page's first load. Two entries: the site footer (`MainLayout`, the one `contentinfo` landmark of the public site) and «Сообщить об ошибке» in `ArticleFooter`. The link carries what the form attaches by itself (`src/shared/feedback.ts`: `feedbackHref` / `readFeedbackRequest`): `type` (`article-error` | `site-problem` | `idea`), `article` (id), `from` (the page the reader came from — a site-relative path only, anything else is dropped) and, when that page was opened by a `?mazhab=` link, the same `mazhab` parameter, so `MazhabProvider` gives the form the mazhab the reader was reading in. The form sends `from` as `pageUrl` (relative, so `Feedback:SiteUrl` never drops it), the article id and the slug of the mazhab from `useMazhab()`, and shows all three (the article title comes from the public navigation tree) before sending, together with the notice that the text, page, article and mazhab become a public GitHub issue and the contact does not. Limits mirror the server's (`FEEDBACK_TEXT_MAX_LENGTH` 4000 with a counter, contact 200); validation errors sit at their field (`aria-invalid`, `aria-describedby`, focus moves to the first one), any other error (429 `too_many_requests` / `feedback_limit_reached`, network) is a focused `role="alert"` above the form and the typed text stays. The trap input `website` is off-screen inside an `aria-hidden` block (`tabindex="-1"`, `autocomplete="off"`, not `hidden`) and its value is sent as it is. Success replaces the form with «Сообщение № N отправлено» (focused `h1`) and a link back to the page. Sending needs JavaScript (no server action). Not there: the admin list of messages (F-04 #163).
- Sources on the page (M-07, #71): the footer's first block, «Источники», is a numbered list built by `collectCitedSources` (`src/shared/articleSources.ts`) from the content DTO — each cited source once, in the order of first citation, with its locators as links back to the citing paragraphs (`#p-{id}`; «в тексте» when a citation has no locator). It lists the sources of **every** opinion, not only those of the reader's mazhab: the list describes the article, and so the server HTML is complete and the same after hydration whatever mazhab the browser stores. In the editor `OpinionSourcesEditor` (under a paragraph and under the selected opinion of a block of opinions; headings cite nothing) attaches entries found in the directory, sets locators and adds a new entry. Left to E-09 (#145): footnote markers inside the text, showing sources next to the opinion that cites them, reordering citations, and a page to edit or delete directory entries (the API has `PUT`/`DELETE /sources/{id}`).
- Author page (P-01, #89): `/authors/:slug?page=…` (`routes/author.tsx`, `pages/AuthorPage.tsx`, helpers in `src/shared/author.ts`) — server-rendered from `GET /authors/{slug}` and the requested page of `/authors/{slug}/articles`; its own route chunk. Shows the avatar, the name (the only h1), the role from `userRole`, the bio as plain text, the links (`rel="nofollow noopener"`) and the articles with dates (the «Обновлено» date only from the day after publication). An author the API does not give — no name, nothing published, an old slug — is the 404 page with a 404 status. The avatar is an arbitrary address until uploads exist (#73): a fixed 96 px box, `loading="lazy"`, `referrerPolicy="no-referrer"`, and the first letter of the name whenever the image is missing or fails. A scholar's degree and institution are shown as self-declared («Указано самим автором…»), never as confirmed, and stay out of the structured data until verification exists (V-01 #117, V-02 #118). Meta: the first page is indexable with canonical `/authors/{slug}`, further pages are `noindex` without a canonical; JSON-LD is `ProfilePage` + `Person` (`personNode`, `personId` in `src/shared/structuredData.ts` — the `@id` an article's `author` will point at, P-06 #94). Author pages are not in the sitemap (there is no public list of authors); crawlers reach them through links. Not there yet: the author line on the article page (P-06 #94). `PageLinks` (`src/components/PageLinks.tsx`) is the pager shared with the search page.
- Document metadata (O-04): `PageMeta` (`src/components/PageMeta.tsx`) renders title ("{page} — mktba"), description, canonical, robots, Open Graph and Twitter Card as React 19 elements hoisted into `<head>` (in the server HTML too); rules live in `src/shared/siteMeta.ts`. Exactly one `PageMeta` is mounted at a time: a route with `handle.ownsMeta` renders its own (home, article, 404), otherwise the root renders a generic `noindex, nofollow` one (admin, sign-in, service pages). Absolute URLs are built on the root loader's `siteUrl` (`PUBLIC_SITE_URL`, else the request origin) via `useSiteUrl()`; the article canonical path comes from `articleHref`.
- Navigation tree (R-09, #45): `components/NavigationTree.tsx`, used by the sidebar (and its mobile drawer) and the admin tree. Collapsed sections are a set of article ids in `localStorage['mktba.navTree.collapsed']` behind `src/shared/navigationTreeState.ts` (`useSyncExternalStore`: the server and the hydrating render see everything expanded, so the server HTML always holds every link of the tree; the saved state applies right after hydration and is shared by all trees on the page and by other tabs). Only collapsed ids are stored — an untouched section is expanded. The ancestors of the current article are expanded (and saved so) whenever the article changes, and its row is scrolled into view; the sidebar search shows the filtered tree fully expanded without toggles (`forceExpanded`) and leaves the saved state alone. A section shows the number of its direct children. Semantics stay native — nested `ul`/`li`, links, disclosure buttons with `aria-expanded` — not `role="tree"`: rows hold real links (crawlers, middle click) and, in the admin, action buttons, which a `treeitem` cannot own cleanly. The WAI-ARIA tree keys are added on top (Up/Down, Right/Left, Home/End over the rows on screen; Tab is unchanged). Large trees are windowed (`components/navigationTree/`): a tree with more than `NAVIGATION_TREE_WINDOWING_THRESHOLD` (300) articles switches, after hydration only, from the nested lists to `WindowedNavigationList` — one flat `ul` as high as all rows, holding only the rows in view plus 10 above and below, each in a fixed 29px slot; the hierarchy is spelled out on every `li` (`aria-level`, `aria-setsize`, `aria-posinset`). The server and the hydrating render always produce the nested lists with every link (crawlers, no mismatch), and a tree at or below the threshold never leaves them. Both modes render the same `NavigationRow` (toggle, link, counter, status badge, admin actions), so the admin tree is windowed too. In windowed mode the arrow keys work on the row model (`flattenVisibleRows`), not on the DOM: the focused row and the current article's row are rendered wherever they are, and a row that is not rendered yet is rendered first and focused then. The visible area is the window cut by every clipping ancestor, so whatever renders the tree needs no props for it. Not in the DOM in this mode: rows out of view (find-in-page and a screen reader's link list see only what is rendered). Nested rows keep `content-visibility: auto` (28px intrinsic height) for the first paint of a large tree before hydration.
- Infobox layout (R-04): `ArticleInfoboxPanel` floats right by the width of its nearest `@container` ancestor (`@2xl`, the article column), not the viewport; whatever renders it must provide that `@container flow-root` wrapper. A bordered or filled block that can sit next to it needs `flow-root` so it ends at the float instead of running under it. Below `sm` the body is collapsed with CSS only (it stays in the server HTML).

**Frontend ↔ Backend:**
- Base URL configured in `mktba.react/src/config.ts` (`http://localhost:5172`)
- CORS allows any loopback / `localhost` origin (Vite dev port `:5173`)
- Access token (15 min) kept in memory only (`src/services/session.ts`); the refresh token is an `httpOnly` cookie (`mktba_refresh`, `Path=/auth`) rotated by `POST /auth/refresh`, which the axios interceptor calls once on a 401 and the app calls on load. Access tokens carry the session id (`mktba_sid`) and `JwtProblemEvents.TokenValidated` rejects them once the session is revoked (README «Сессии»). Protected routes under `/admin/*`
- HTTP via Axios; server state via React Query
- Global mazhab selection stored in `localStorage['mktba.mazhab']`, exposed through `MazhabContext`; the picker (`components/mazhab/MazhabSelector.tsx`) sits in the public header and shows a one-time hint (`localStorage['mktba.mazhabHintSeen']`). A shared link `?mazhab=<system school slug>` (R-03, #39) wins over the saved choice while the parameter is in the URL and never overwrites it; choosing by hand saves the choice and drops the parameter. The canonical schools are prefetched by the public layout's loader (`routes/public-layout.tsx`), not by pages: a query a component above a page's `HydrationBoundary` already observes gets that boundary's data only in an effect, too late for the server HTML — for the same reason `MazhabProvider` (above the layout) resolves the link slug through a query key of its own

**Database:** PostgreSQL 16. Connection string `ConnectionStrings:DefaultConnection`; Development uses `appsettings.Development.json`, matching `docker-compose.yml` (service `postgres`).

## Coding conventions

- English for all code symbols; Russian may appear in UI strings/comments/AI prompts.
- UI text lives only in `mktba.react/src/localization/locales/ru/*.json`; ESLint (`i18next/no-literal-string`) fails on hard-coded JSX text and user-facing attribute strings in `src/**/*.tsx`.
- No dead code, no commented-out blocks, no TODOs without an issue reference.
- No unrelated refactors mixed into task-specific changes.
- Keep public API/DTO contracts documented.
- API errors are `application/problem+json` bodies (`ApiProblemDetails`: `title`, `status`, `code`, optional `params`, `traceId`). Add a new error to `Mktba.Application/Exceptions/AppErrors.cs` (stable snake_case code) and its Russian text to `apiErrors` in `mktba.react/src/localization/locales/ru/shared.json`; the UI shows only the translation by code, never the server's `title`.

```
feat:      new functionality

refactor:  internal restructuring without behavior change
test:      tests only
docs:      documentation only
chore:     maintenance/tooling

```
Scope is optional: `fix(api): validate node parent before update`

## Testing

- Unit tests for domain logic; integration tests for DB/API boundaries.
- Prefer real behavior over mocks. Assert observable outcomes.
- Test names: describe scenario + expected result (Given/When/Then structure).
- Cover happy path, at least one edge case, and one failure path per behavior change.
- For bug fixes, add a regression test.
