# mktba

**mktba** (مكتبة — «библиотека») — open-source исламская wiki-платформа. Статьи организованы в иерархическое дерево, каждая содержит параграфы, а каждый параграф может иметь несколько мнений разных мазхабов (школ исламского права). По умолчанию поддерживаются четыре канонические суннитские школы — Hanafi, Maliki, Shafi'i, Hanbali — плюс произвольные пользовательские школы per-article.

Проект построен как hard fork [WikiWeaver](https://github.com/shoraLBRT/WikiWeaver) с переработанной доменной моделью, брендом и целевой аудиторией.

## Ключевые возможности

* **Иерархия статей** — дерево разделов и подразделов в боковой панели.
* **Мнения мазхабов** — inline-блок в статье показывает альтернативные мнения, помеченные одной или несколькими школами.
* **Выбор мазхаба в шапке** — глобальный выбор школы по умолчанию, применяется ко всем статьям; при первом визите — короткая подсказка, что это; ссылкой `?mazhab=<slug школы>` можно поделиться страницей с выбранным мазхабом.
* **Поиск** — полнотекстовый, с русской морфологией (PostgreSQL FTS): по названию, описанию, тегам и текстам мнений; страница результатов `/search?q=…` с подсветкой совпадений, вызов по `Ctrl+K`.
* **Markdown-редактор** для админов с поддержкой inline-сносок (GFM footnotes).
* **AI-помощник** (опционально) для стилизации markdown.
  Провайдера по умолчанию нет: пока в админке (`/admin?section=aiProvider`) не заданы адрес,
  модель и API-ключ, функции ИИ выключены, а API отвечает `ai_provider_not_configured`.
* **Админ-панель** — управление статьями, системными школами, AI-настройками, приглашениями с ролью (одноразовые, со сроком, отзываемые) и ролями пользователей.

## Стек

* **Backend**: ASP.NET Core 8 Minimal API, Clean DDD.
* **База данных**: PostgreSQL 16 + EF Core 8.
* **Frontend**: React 19 + TypeScript + React Router v7 (framework mode, SSR публичных страниц) + React Query v5 + Tailwind CSS v4 + Vite.
* **Auth**: короткий JWT Bearer в памяти + ротируемый refresh-токен в `httpOnly`-cookie, одноразовые приглашения с ролью (Reader/Author/Scholar/Admin) для регистрации.

## Локальный запуск

### Backend

```bash
docker compose up -d postgres    # поднять локальный PostgreSQL
dotnet restore Mktba.sln
dotnet build Mktba.sln           # без имени решения MSBuild падает (MSB1011: рядом docker-compose.dcproj)
dotnet run --project Mktba.Api   # :5172, в Development при старте применяет миграции и 4 системные школы
```

Тесты: `dotnet test Mktba.sln`. Почти все идут на InMemory-провайдере, но тесты поиска
(`ArticleSearchTests`) работают с настоящим PostgreSQL: каждый класс создаёт на сервере свою базу
`mktba_test_<guid>` со всеми миграциями и удаляет её. Сервер — сервис `postgres` из
`docker-compose.yml`; другой задаётся переменной `MKTBA_TEST_DB_CONNECTION` (строка подключения
Npgsql, имя базы в ней не используется). Без PostgreSQL эти тесты падают, а не пропускаются.

Строка подключения из коробки: `dotnet run` стартует в Development, а
`appsettings.Development.json` смотрит в БД `mktba` сервиса `postgres` из `docker-compose.yml`
(пользователь `mktba`, пароль `mktba_dev` — dev-значения из того же файла). Первого админа
создаёт форма входа (`/admin/login` на `:5173`) или `POST /auth/register`, демо-контент — скрипт:

```bash
node scripts/seed-demo-content.mjs --email admin@mktba.local --password '<пароль>'
```

#### Локальные настройки

Свои значения для своей машины (другая БД, пароль, ключ AI) кладите в
`Mktba.Api/appsettings.local.json` — он в `.gitignore` и `.dockerignore`, образец —
`Mktba.Api/appsettings.local.example.json`:

```bash
cp Mktba.Api/appsettings.local.example.json Mktba.Api/appsettings.local.json
```

Порядок источников (последний побеждает): `appsettings.json` → `appsettings.{Environment}.json`
→ `appsettings.local.json` → user-secrets (Development) → переменные окружения
(`ConnectionStrings__DefaultConnection=...`) → аргументы командной строки.

#### Миграции БД (X-03)

API сам применяет миграции при старте только при `Database:MigrateOnStartup=true` — так стоит в
`appsettings.Development.json` (локальный запуск, e2e). В любом другом окружении (Production,
Staging, контейнер) он схему не трогает: проверяет, что неприменённых миграций нет, и иначе не
стартует с сообщением, сколько их и какой командой применить. Миграции применяет тот же бинарник
отдельной командой — она применяет миграции, досоздаёт справочные данные (4 системные школы
с английскими названиями, `SystemSchoolSeeder`) и завершается, ничего не обслуживая:

```bash
dotnet Mktba.Api.dll --migrate                     # опубликованная сборка
dotnet run --project Mktba.Api -- --migrate        # из исходников
docker run --rm -e ConnectionStrings__DefaultConnection=... <образ> --migrate   # ENTRYPOINT образа — API
```

Команда идемпотентна: повторный запуск на актуальной базе ничего не меняет. Порядок деплоя —
сначала `--migrate`, потом новая версия API (так делает деплой из CI, X-02 #64, ниже).
Демо-контента в API нет вовсе — его создаёт только скрипт `scripts/seed-demo-content.mjs` (ниже).

#### Ключ подписи JWT

Ключ (`Auth:JwtSigningKey`) в `appsettings.json` не хранится. В Development (`dotnet run`
с профилем запуска) используется dev-ключ из `appsettings.Development.json`. В любом другом
окружении (Production, Staging, контейнер) API не стартует, если ключ не задан, короче
32 байт (256 бит, минимум для HS256) или совпадает с одним из закоммиченных в репозиторий
плейсхолдеров. Задать ключ:

```bash
# переменная окружения (прод, контейнер: docker run -e Auth__JwtSigningKey=...)
export Auth__JwtSigningKey="$(openssl rand -base64 48)"
# или, для локальной разработки, user-secrets
dotnet user-secrets --project Mktba.Api set "Auth:JwtSigningKey" "$(openssl rand -base64 48)"
```

Окружение `OpenApi` (генерация контракта, `npm run gen:api`) токенов не выпускает и ключ не проверяет.

#### Сессии (U-03)

Вход (`POST /auth/login`, `/auth/register`) возвращает короткий access-токен в теле и ставит
refresh-токен в cookie `mktba_refresh`. Фронтенд держит access-токен **только в памяти**
(не в `localStorage`); после перезагрузки страницы и на любой `401` он один раз вызывает
`POST /auth/refresh` и повторяет запрос. Каждый refresh ротирует токен; повторное предъявление
уже заменённого токена (признак кражи) завершает всю сессию этого устройства. В базе лежит
только SHA-256 токена (таблица `RefreshSessions`).

| Ключ `Auth` | Что | По умолчанию |
| --- | --- | --- |
| `AccessTokenLifetimeMinutes` | срок access-токена | 15 |
| `RefreshTokenLifetimeDays` | срок refresh-токена, скользящий (продлевается каждым refresh) | 30 |
| `RefreshCookiePath` | `Path` cookie: путь `/auth` API так, как его видит браузер | `/auth` |

- **Cookie:** `HttpOnly; SameSite=Strict; Path=/auth; Secure`. `Secure` снимается только в
  Development (локальный http); в любом другом окружении API нужно отдавать по https.
- **CSRF:** `POST /auth/refresh` и `/auth/logout` требуют заголовок `X-Requested-With` (иначе `403`).
  Вместе с `SameSite=Strict` этого достаточно: чужой сайт не отправит cookie, а заголовок со
  стороннего origin пройдёт только через CORS-preflight, который API для него не разрешает.
- **Выход:** `POST /auth/logout` — это устройство; `POST /auth/logout-all` — все устройства;
  `GET /auth/sessions` / `DELETE /auth/sessions/{id}` — список устройств и завершение одного
  (в админке — раздел «Сессии»). Access-токены несут id сессии, и API принимает их, только пока
  сессия жива, поэтому выход действует сразу, а не через 15 минут.
- **Развёртывание:** фронтенд и API должны быть *same-site* (например, `mktba.ru` и
  `api.mktba.ru`, или один хост с прокси `/api` → API — тогда `Auth__RefreshCookiePath=/api/auth`).
  Стенд (X-01) так и устроен: сайт `mktba.ru`, API `api.mktba.ru`, путь cookie по умолчанию.
  CORS с credentials разрешает loopback-origin'ы (локальная разработка: Vite `:5173` и API `:5172` —
  разные origin, но один site) и точные origin'ы из `Cors:AllowedOrigins`
  (`Cors__AllowedOrigins__0=https://mktba.ru`; схема, хост и порт, без пути — иначе API не стартует).
  Токены, выданные до U-03 (без id сессии), больше не принимаются — после обновления всем нужно
  войти заново.

#### Профиль пользователя (U-07)

У каждого пользователя есть профиль: имя, адрес (slug), ссылка на аватар, текст о себе, до пяти
ссылок и — со слов пользователя — учёная степень и учреждение. Все поля необязательны; заполняются
в админке в разделе «Мой профиль» (`/admin/profile`, доступен любой роли) или через `PUT /profile`,
администратор может править чужой профиль через `PUT /users/{id}/profile`.

- Без имени пользователь не показывается читателям нигде: почта и её часть никогда не подставляются.
- Адрес профиля строится по тем же правилам, что адрес статьи (транслитерация из имени или вручную),
  и уникален. При смене старый адрес не сохраняется: редиректов нет.
- Аватар — это ссылка `https://…` или путь на сайте `/…`; форма профиля заполняет её загрузкой
  (`POST /uploads/avatar`, см. «Загрузка файлов»).
- Читателям профиль отдаёт `GET /authors/{slug}` — без почты и id — и только если у пользователя есть
  имя и он автор или соавтор хотя бы одной опубликованной статьи; иначе `404 author_not_found`.
- Степень и учреждение читателям отдаются только у пользователей с ролью `Scholar` и не являются
  подтверждёнными: подтверждение — задача эпика верификации (V-01, V-02).
- Страница автора для читателей — `/authors/{slug}` (P-01, #89): аватар, имя, роль, текст «о себе»,
  ссылки и список статей с датами (`GET /authors/{slug}/articles` — только то, что читатель может
  открыть). Степень и учреждение учёного показаны с пометкой «указано самим автором». Страница
  индексируется, но в sitemap не входит; на неё ведёт строка автора на странице статьи (P-06, #94):
  «Автор: …» под заголовком, только для пользователей с отображаемым именем.

#### Ограничение частоты запросов

Секция `RateLimiting` в `appsettings.json` (фиксированное окно; превышение — `429` с `Retry-After`):

| Лимит | Эндпоинты | Раздел | По умолчанию |
| --- | --- | --- | --- |
| `Auth` | `POST /auth/login`, `POST /auth/register` | IP клиента | 10 запросов / 60 с |
| `Session` | `POST /auth/refresh`, `POST /auth/logout` | IP клиента | 60 запросов / 60 с |
| `Ai` | `POST /admin/ai-style`, `POST /admin/ai-check` | id пользователя | 20 запросов / 3600 с |
| `Feedback` | `POST /feedback` | IP клиента | 5 запросов / 600 с |

Переопределение: `RateLimiting__Auth__PermitLimit=...`, `RateLimiting__Ai__WindowSeconds=...`.

**За обратным прокси.** По умолчанию IP — адрес соединения, `X-Forwarded-For` не учитывается:
за прокси все посетители делили бы один лимит на IP. Перечислите свои прокси в секции
`ForwardedHeaders` — тогда адрес посетителя берётся из `X-Forwarded-For`, но только в запросах,
пришедших от этих прокси (заголовок от кого угодно другого игнорируется):

| Ключ | Значение |
| --- | --- |
| `ForwardedHeaders:KnownProxies` | IP-адреса прокси, например `ForwardedHeaders__KnownProxies__0=127.0.0.1` |
| `ForwardedHeaders:KnownNetworks` | Сети прокси в записи CIDR, например `ForwardedHeaders__KnownNetworks__0=172.18.0.0/16` (сеть Docker) |
| `ForwardedHeaders:ForwardLimit` | Сколько прокси стоит перед API (по умолчанию 1) |

От этих прокси читаются `X-Forwarded-For` и `X-Forwarded-Proto` (прокси снимает TLS, а схема
запроса остаётся `https`, как у посетителя); хост не меняется — прокси передаёт исходный. Прокси
должен сам выставлять эти заголовки (Caddy делает это по умолчанию; в nginx —
`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` и `X-Forwarded-Proto $scheme`).

#### Обратная связь и GitHub App (F-02, F-03)

`POST /feedback` принимает сообщение посетителя без входа, сохраняет его в таблицу
`FeedbackMessages` и сразу отвечает `202`. Issue в репозитории создаёт фоновый обработчик
(`FeedbackDeliveryWorker`) от имени GitHub App — с метками `feedback` и `needs-triage`. Репозиторий
публичный (решение D9), поэтому в issue попадают тип, текст, адрес страницы, статья и мазхаб, а
контакт остаётся только в БД: в issue написано лишь «контакт оставлен» и номер обращения. IP и
User-Agent не сохраняются.

Пока GitHub недоступен или не принимает ключ, обращение ждёт в состоянии `Pending` и повторяется
с растущей паузой (от `RetryBaseSeconds` до `RetryMaxSeconds`, без ограничения числа попыток);
очередь — сама таблица, перезапуск её не теряет. Причина последней неудачи — в столбце `LastError`.
`Failed` получает только обращение, которое GitHub отклонил как некорректное (422).

**Без настройки** (так по умолчанию в разработке, CI и e2e) обращения принимаются и копятся в
`Pending` с нулём попыток; после настройки они уйдут сами.

Настройка — секция `Feedback`:

| Ключ | Значение |
| --- | --- |
| `Feedback:GitHub:AppId` | App ID приложения (в `appsettings.json` — `5514770`, приложение `feedback-machine`) |
| `Feedback:GitHub:Owner`, `Feedback:GitHub:Repository` | Репозиторий для issues (в `appsettings.json` — `shoraLBRT/mktba`) |
| `Feedback:GitHub:PrivateKeyPath` | Путь к приватному ключу приложения (`.pem`) **вне репозитория** |
| `Feedback:GitHub:PrivateKey` | Сам ключ текстом PEM — для переменной окружения; переводы строк можно записать как `\n`. Важнее пути |
| `Feedback:GitHub:Enabled` | `false` выключает доставку, даже если ключ задан (так запускается API в e2e) |
| `Feedback:Delivery:*` | `PollIntervalSeconds` (30), `BatchSize` (20), `RetryBaseSeconds` (60), `RetryMaxSeconds` (3600) |
| `Feedback:Intake:MaxPerHour` | Сколько обращений от всех посетителей вместе сохраняется за любые 60 минут (30); `0` — без ограничения |
| `Feedback:SiteUrl` | Публичный адрес сайта (`https://mktba.ru`). Если задан, адрес страницы с другого источника в обращение не попадает |

Локально — путь к ключу в `Mktba.Api/appsettings.local.json`:

```json
{ "Feedback": { "GitHub": { "PrivateKeyPath": "C:/keys/feedback-machine.private-key.pem" } } }
```

В продакшене — переменные окружения: `Feedback__GitHub__PrivateKeyPath=/run/secrets/feedback.pem`
или `Feedback__GitHub__PrivateKey=...`. Ключ не кладите в репозиторий и в образ.

Что нужно от GitHub:

1. Приложению — права **Issues: Read and write** и **Metadata: Read-only**; оно должно быть
   установлено на репозиторий из `Owner`/`Repository` (id установки API находит сам).
2. В репозитории заранее создайте метки `feedback` и `needs-triage`. Если issue создан без них,
   в логе API будет предупреждение.

Проверка вживую: задайте ключ, запустите API и отправьте
`curl -X POST http://localhost:5172/feedback -H "Content-Type: application/json" -d '{"type":"Idea","text":"проверка"}'`
— в течение `PollIntervalSeconds` в репозитории появится issue, а в строке таблицы — `Delivered` и
номер issue. Автотесты GitHub не вызывают.

**Защита и приватность (F-03).** Эндпоинт открыт всем, а issue публичный, поэтому:

- **Частота.** Не больше 5 запросов за 10 минут с одного IP (`RateLimiting:Feedback`) — `429`
  с кодом `too_many_requests`; не больше `Feedback:Intake:MaxPerHour` сохранённых обращений в час
  от всех посетителей вместе — `429` с кодом `feedback_limit_reached` (так множество адресов сразу
  не завалит таблицу и issues репозитория). Оба ответа — с `Retry-After`. Общий лимит считается по
  таблице, поэтому переживает перезапуск; запросы, отброшенные ловушкой или проверкой, его не
  расходуют. IP нужен только счётчику в памяти: он не сохраняется и не пишется в лог вместе с
  обращением.
- **Ловушка для ботов.** Поле `website` в теле запроса: форма рисует его скрытым от людей
  (`tabindex="-1"`, `autocomplete="off"`, `aria-hidden`, спрятано стилями) и отправляет как есть.
  Если в нём есть что-то кроме пробелов, ответ выглядит как обычный успех (`202` с номером), но
  ничего не сохраняется и никуда не отправляется.
- **Текст посетителя в issue — только текст.** Он попадает в блок кода, ограда которого длиннее
  любой серии обратных кавычек в тексте; адрес страницы, название статьи и мазхаба — в строчный
  код. Внутри кода GitHub ничего не разбирает: `@`-упоминания не уведомляют людей и команды,
  `#123`, `owner/repo#1`, хеши коммитов и ссылки на issues не создают перекрёстных ссылок,
  картинки, заголовки, ссылки и HTML не работают, а выйти из блока текст не может — значит, не
  может и подделать скрытую метку `<!-- mktba-feedback:… -->`. Метка засчитывается, только если
  это последняя строка issue. Символы, меняющие направление текста (bidi-переопределения и
  изоляты), удаляются. Плата за надёжность: длинные строки в issue не переносятся, а адрес
  страницы не кликается.
- **Длины.** Текст — до 4000 символов, контакт — до 200, адрес страницы — до 2048; тело issue
  в худшем случае — около 19 тысяч символов при лимите GitHub 65 536.
- **Адрес страницы.** Абсолютный адрес принимается только со своего сайта, если задан
  `Feedback:SiteUrl`; чужой адрес молча отбрасывается, обращение сохраняется. Относительные пути
  (`/salat...`) принимаются всегда.

Перед включением доставки на публичном сервере: если API стоит за прокси — настройте
`ForwardedHeaders` (иначе лимит на IP общий для всех посетителей), задайте `Feedback:SiteUrl`.
Заголовок issue содержит название опубликованной статьи как есть: его пишут авторы сайта, не
посетитель.

**Форма (F-01, #66).** Страница `/feedback` (не индексируется) открывается из подвала сайта и по
ссылке «Сообщить об ошибке» внизу статьи. Ссылка несёт то, что форма прикладывает сама:
`?type=article-error|site-problem|idea&article=<id>&from=<путь страницы>`; мазхаб берётся из выбора
читателя (или из `?mazhab=` ссылки, по которой он пришёл). Перед отправкой форма показывает, что
уйдёт вместе с текстом, и предупреждает, что текст, адрес страницы, статья и мазхаб станут
открытым issue, а контакт — нет. Для отправки нужен JavaScript. Списка обращений в админке пока
нет (F-04, #163).

#### Яндекс Вебмастер, Google Search Console и IndexNow (O-12, #61)

Подтверждение прав на сайт — мета-тегами в `<head>` каждой страницы. Токены задаются фронтенд-серверу
при запуске (`YANDEX_VERIFICATION`, `GOOGLE_SITE_VERIFICATION`, см. таблицу в разделе Frontend); не
заданы — тегов нет. Токен — только буквы, цифры, `-` и `_`, иначе он игнорируется.

IndexNow: когда статья публикуется или снимается с публикации (Published → Archived), API в фоне
сообщает её адрес `{SiteUrl}/{slug}` IndexNow-эндпоинту (по умолчанию Яндекс; участники IndexNow —
Яндекс, Bing и другие — делятся адресами между собой; Google IndexNow не поддерживает и узнаёт о
страницах из `sitemap.xml`). Изменения за `BatchDelaySeconds` уходят одним запросом. Очередь — в
памяти: при перезапуске или ошибке уведомление теряется, страница всё равно есть в карте сайта.
Ключ поисковики читают по адресу `/indexnow-key.txt` (его отдаёт фронтенд, беря ключ у API:
`GET /seo/indexnow-key`; пока IndexNow выключен — `404`).

| Параметр | Назначение |
| --- | --- |
| `IndexNow:Key` | ключ: 8–128 символов `a-z`, `A-Z`, `0-9`, `-` (например, `New-Guid` без фигурных скобок). Ключ публичный по смыслу протокола |
| `IndexNow:SiteUrl` | публичный адрес сайта без пути (`https://mktba.ru`) — на нём строятся адреса |
| `IndexNow:Endpoint` | куда отправлять (по умолчанию `https://yandex.com/indexnow`) |
| `IndexNow:BatchDelaySeconds` | пауза перед отправкой, чтобы массовое действие ушло одним запросом (5) |
| `IndexNow:Enabled` | `false` выключает отправку, даже если ключ задан (так запускается API в e2e) |

Без `Key` и `SiteUrl` IndexNow выключен. В тестах наружу ничего не уходит: `MktbaApiFactory` заменяет
клиент IndexNow, e2e-API запускается с `IndexNow__Enabled=false`.

Что сделать владельцу: подтвердить сайт в Яндекс Вебмастере и Google Search Console способом
«мета-тег» (токен — в переменные фронтенда), задать `IndexNow__Key` и `IndexNow__SiteUrl` API, после
выкладки проверить, что `https://mktba.ru/indexnow-key.txt` отдаёт ключ, и добавить
`https://mktba.ru/sitemap.xml` в обоих сервисах.

#### Загрузка файлов (U-08, #73)

`POST /uploads/avatar` (любой вошедший пользователь) и `POST /uploads/images` (авторы и админы)
принимают картинку полем `file` формы `multipart/form-data` и отвечают `201` с
`{ url, contentType, width, height, sizeBytes }`. Профиль сам не меняется: форма «Мой профиль»
кладёт `url` в поле аватара, и он сохраняется вместе с профилем.

- **Проверка.** Формат определяется по первым байтам файла, а не по имени и не по `Content-Type`
  клиента: принимаются только JPEG, PNG и WebP (SVG, GIF, HTML — `upload_type_unsupported`).
  Размер — до `Uploads:MaxBytes` (10 МБ), картинка — до `Uploads:MaxPixels` (40 Мп; проверяется
  по заголовку до декодирования).
- **Обработка** (SkiaSharp, MIT). Картинка поворачивается по EXIF, уменьшается (аватар — до
  512 px по длинной стороне, картинка статьи — до 2048 px) и заново кодируется в WebP, поэтому
  от файла остаются только пиксели: EXIF (камера, GPS), XMP и прочие метаданные не сохраняются.
- **Имена.** Файл хранится под случайным именем `<32 hex>.webp`; ничего из присланного в имя не
  попадает. Файлы не меняются.
- **Учёт.** Каждая загрузка записывается в таблицу `StoredFiles`: кто и когда загрузил, размер,
  тип, ширина и высота, а после проверки — где файл используется (аватар, статья, ревизия,
  черновик, профиль или источник).
- **Чистка.** Фоновая задача (при старте и каждые `Uploads:Cleanup:IntervalHours`, 6 ч) смотрит
  файлы старше `Uploads:Cleanup:UnusedDays` (30 дней) и ищет их имя в аватарах, тексте и
  оформлении статей, всех ревизиях, черновиках, профилях и источниках. Файл, на который ничто не
  ссылается, помечается; если и через `UnusedDays` после пометки на него никто не сослался, он
  удаляется из хранилища, а запись остаётся с датой удаления. `Uploads:Cleanup:DeleteUnused=false`
  оставляет только пометки. Файлы, загруженные до появления учёта, не удаляются.
- **Раздача.** `GET /files/{name}` — публично, с типом `image/webp`, `X-Content-Type-Options:
  nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` и кешем на год (`immutable`).
- **Частота.** `RateLimiting:Uploads` — 30 загрузок в час на пользователя.

Где лежат файлы — секция `Storage`:

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `Storage:Provider` | `Local` | `Local` — каталог на машине API; `S3` — бакет S3-совместимого хранилища |
| `Storage:Local:RootPath` | `App_Data/uploads` | каталог (относительный путь — от корня API); на сервере — на постоянном томе |
| `Storage:S3:ServiceUrl` | — | адрес сервиса, например `https://storage.yandexcloud.net` или `http://localhost:9000` (MinIO); пусто — сам AWS |
| `Storage:S3:Region` | `ru-central1` | регион подписи |
| `Storage:S3:Bucket` | — | бакет (обязателен для `S3`) |
| `Storage:S3:KeyPrefix` | — | префикс ключей, например `uploads/` |
| `Storage:S3:AccessKey` / `SecretKey` | — | ключи доступа — только в user secrets, `appsettings.local.json` или переменных окружения (`Storage__S3__SecretKey`); пусто — стандартная цепочка AWS |
| `Storage:S3:ForcePathStyle` | `false` | `true` для MinIO |
| `Uploads:PublicBaseUrl` | — | адрес, под которым файлы доступны читателям (публичный бакет или CDN), с `/` на конце; пусто — `GET /files/` этого же API |
| `Uploads:Cleanup:DeleteUnused` | `true` | удалять ли неиспользуемые файлы; `false` — только помечать |
| `Uploads:Cleanup:UnusedDays` | `30` | срок в днях: возраст файла до первой проверки и сколько он должен пробыть неиспользуемым |
| `Uploads:Cleanup:IntervalHours` | `6` | как часто запускается чистка |

Объекты пишутся без ACL (приватными): если бакет не публичный, оставьте `PublicBaseUrl` пустым —
API сам отдаст файл из бакета. Если API стоит за прокси, а `PublicBaseUrl` пуст, настройте
`ForwardedHeaders`, иначе в `url` попадёт внутренний адрес и схема.

### Frontend

```bash
cd mktba.react
npm install
npm run dev
```

Dev-сервер (`react-router dev`, Vite с серверным рендером) слушает `:5173`, API — `:5172`.

Публичные страницы (главная, статья, 404) рендерятся на сервере: HTML уже содержит дерево статей,
заголовок, все параграфы статьи и её метаданные. Статья живёт по адресу `/{slug}`; старый slug и

### E2E-дым (Playwright)

Сценарии в `mktba.react/e2e`: открыть статью, сменить мазхаб, войти, создать и отредактировать
статью, привести источник и увидеть его под опубликованной статьёй, открыть предпросмотр черновика (стили в iframe, мазхаб предпросмотра, ширина телефона). Тесты гоняются против настоящего API и **отдельной одноразовой БД** — не направляйте их на
базу, данные которой нужны: тест создаёт админа и статьи.

```bash
docker compose up -d postgres
cd mktba.react
npx playwright install chromium          # один раз
export E2E_ADMIN_PASSWORD="$(node -e "console.log(require('crypto').randomBytes(18).toString('base64url'))")"
npm run test:e2e
docker exec mktba_postgres psql -U mktba -d postgres -c "DROP DATABASE mktba_e2e WITH (FORCE);"
```

Playwright сам поднимает API (`dotnet run`, `:5172`, БД `mktba_e2e`, миграции при старте,
случайный JWT-ключ на прогон) и SSR dev-сервер (`:5173`). Порт `:5172` должен быть свободен: уже запущенный
API не переиспользуется, чтобы тест не попал в базу с нужными данными; dev-сервер переиспользуется. Проект `setup` (`e2e/setup.mjs`) регистрирует первого админа
(`E2E_ADMIN_EMAIL`, по умолчанию `e2e@mktba.local`, пароль `E2E_ADMIN_PASSWORD`) или входит им,
если он уже есть, и заливает `scripts/demo-content.json`, если дерево статей пустое, поэтому
повторный прогон по той же БД работает с тем же паролем. Другая БД — `E2E_DB_CONNECTION`
(строка подключения Npgsql). В CI это джоб `e2e`; при падении HTML-отчёт лежит в артефакте
`playwright-report`.

## Развёртывание (X-01)

Стенд — staging или продакшен — описан в `deploy/`: `docker-compose.yml`, `Caddyfile` и
`.env.example`. Корневой `docker-compose.yml` — только база для локальной разработки.

```text
интернет ─443/80─> caddy ─┬─ mktba.ru ─────> web (react-router-serve, :3000) ─┐ API_INTERNAL_URL
                          └─ api.mktba.ru ─> api (ASP.NET, :8080) <────────────┘ http://api:8080
                                             └─> postgres (наружу не открыт)
```

| Сервис | Образ | Что делает |
| --- | --- | --- |
| `caddy` | `caddy:2.10-alpine` | единственный, кто открывает порты; сам получает и продлевает сертификаты Let's Encrypt (тома `caddy_data`, `caddy_config`) |
| `web` | `mktba.react/Dockerfile` | SSR-сервер; `VITE_API_BASE_URL=https://<API_HOST>` зашит при сборке, поэтому у каждого стенда свой образ |
| `migrate` | `Mktba.Api/Dockerfile` | `--migrate`: миграции и справочные данные, потом выход; `api` стартует только после его успеха |
| `api` | `Mktba.Api/Dockerfile` | API; загрузки — `Storage:Provider=Local` на томе `uploads` (до беты, решение владельца 2026-11-21) |
| `postgres` | `postgres:16-alpine` | база на томе `pgdata` |

Решения стенда:

- **Два хоста одного сайта:** `mktba.ru` — сайт, `api.mktba.ru` — API. Они same-site, поэтому
  refresh-cookie (`SameSite=Strict`, `Path=/auth`) работает без изменений; браузер ходит в API
  по CORS с credentials, и `Cors__AllowedOrigins__0=https://<SITE_HOST>` разрешает ровно сайт.
- **TLS снимает Caddy.** API доверяет `X-Forwarded-For` / `X-Forwarded-Proto` только из сети
  `proxy` с фиксированной подсетью (`PROXY_SUBNET`, по умолчанию `172.30.63.0/24`), поэтому лимиты
  считаются по IP посетителя, а ссылки на загрузки — `https://<API_HOST>/files/...`.
- **Staging = тот же файл с другим `.env`:** `COMPOSE_PROJECT_NAME=mktba-staging`,
  `SITE_HOST=staging.mktba.ru`, `API_HOST=api.staging.mktba.ru`, `ASPNETCORE_ENVIRONMENT=Staging`.

Запуск на сервере (Docker с плагином compose):

```bash
cp deploy/.env.example deploy/.env   # заполнить; файл в .gitignore и в репозиторий не попадает
docker compose -f deploy/docker-compose.yml up -d --build
```

Что нужно до первого запуска:

1. DNS: записи A/AAAA `SITE_HOST` и `API_HOST` на сервер; открытые порты 80 и 443 (TCP, 443/UDP для HTTP/3).
2. В `deploy/.env`: `ACME_EMAIL`, `POSTGRES_PASSWORD`, `JWT_SIGNING_KEY` (`openssl rand -base64 48`);
   по желанию — `FEEDBACK_GITHUB_PRIVATE_KEY` (PEM одной строкой с `\n`), `METRIKA_ID`, а для
   поисковиков (O-12) — `INDEXNOW_KEY` (уходит в `IndexNow__Key`; `IndexNow__SiteUrl` = `https://<SITE_HOST>`),
   `YANDEX_VERIFICATION` и `GOOGLE_SITE_VERIFICATION` (переменные `web`). `/indexnow-key.txt`,
   `robots.txt` и карты сайта отдаёт `web`, как и остальные страницы.
3. Сразу после первого запуска зарегистрировать первого админа на `https://<SITE_HOST>/admin/login`:
   первая регистрация без приглашения становится админом.
4. Резервные копии базы и тома `uploads` делает сервис `backup` (X-04, «Резервные копии» ниже);
   копию на другую машину настраивает владелец.

CI на каждом PR (джоб `docker`) проверяет `deploy/docker-compose.yml` и `Caddyfile`, собирает оба
образа, ничего не публикуя, и прогоняет `scripts/test-deploy.sh`: временный стенд из этих образов
разворачивается `deploy.sh`, обновляется на второй тег и откатывается обратно; затем
`scripts/test-backup.sh` (резервные копии, ниже). Джоб `actionlint`
проверяет workflow.

### Деплой из CI (X-02)

Workflow `Deploy` (`.github/workflows/deploy.yml`) публикует образы в GHCR и разворачивает стенд
по SSH скриптом `deploy/deploy.sh`. Из PR он не запускается и ничего не публикует.

| Событие | Образы | Стенд |
| --- | --- | --- |
| push в `main` | `ghcr.io/<owner>/mktba-api:sha-<коммит>` | `staging` получает `sha-<коммит>` |
| релиз (release-please, `release.yml` вызывает `Deploy`) | `mktba-api:<версия>` и `:sha-<коммит>` | `production` получает `<версия>` (например `1.4.0`) |
| ручной запуск (Actions → Deploy → Run workflow) | пустой `tag` — собрать выбранный коммит | выбранный стенд; `tag` — развернуть уже опубликованные образы (откат) |

Образ `web` у каждого стенда свой (в него зашит `VITE_API_BASE_URL`), поэтому он собирается в джобе
деплоя и называется `mktba-web:<тег>-<стенд>` (`MKTBA_WEB_TAG_SUFFIX` в `docker-compose.yml`).
Образ API один на все стенды.

Порядок одного деплоя (`deploy.sh deploy <префикс> <тег> -<стенд>`):

1. на сервер копируются `docker-compose.yml`, `Caddyfile`, `deploy.sh` (`.env` лежит там и не трогается);
2. `docker compose pull` образов `migrate`, `api`, `web`;
3. **миграции отдельным шагом:** `docker compose run --rm migrate` (поднимает `postgres`, применяет
   миграции и справочные данные новым образом и завершается);
4. только если миграции прошли — `api` и `web` переключаются на новые образы (`up -d --no-deps --wait`),
   `caddy` поднимается, если не запущен;
5. запись `<префикс> <тег> <суффикс>` дописывается в `.deploy-history`; CI проверяет
   `https://<API_HOST>/schools/system` и `https://<SITE_HOST>/`.

Упавший pull или миграция оставляют работающие `api` и `web` как были.

**Откат:** ручной запуск `Deploy` с нужным стендом и прошлым тегом (`1.3.0`, `sha-1a2b3c4`; для стенда
годится тег, который на нём уже был: только для него есть образ `web`) или на сервере
`bash <DEPLOY_PATH>/deploy.sh rollback` (предыдущая запись `.deploy-history`; `deploy.sh status` —
текущая). Откат не отменяет миграции, поэтому каждая миграция должна оставлять рабочей предыдущую
версию: сначала добавляем, удаляем — в следующем релизе.

**Что нужно от владельца, чтобы деплой заработал** (до этого джоб `deploy` пропускается, а образ
API всё равно публикуется на каждый push в `main`):

1. Сервер: Linux с Docker Engine и плагином compose, пользователь для деплоя в группе `docker`,
   каталог `DEPLOY_PATH` (по умолчанию `/opt/mktba`) с заполненным `.env` из `deploy/.env.example`
   (переменные `MKTBA_*` в нём не задавать — их передаёт `deploy.sh`), DNS и порты — как выше.
   Staging и production могут жить на одном сервере в разных каталогах (`COMPOSE_PROJECT_NAME` разный),
   но порты 80/443 займёт только один Caddy — тогда нужны разные серверы или общий прокси.
2. SSH-ключ только для деплоя: `ssh-keygen -t ed25519 -N '' -f mktba-deploy`, публичную часть — в
   `~/.ssh/authorized_keys` пользователя деплоя.
3. GitHub → Settings → Environments: `staging` и `production`. У `production` — Required reviewers
   (владелец) и Deployment branches: только `main`. В каждом окружении:
   - секрет `DEPLOY_SSH_KEY` — приватный ключ;
   - переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` (вывод `ssh-keyscan -t ed25519 <host>`,
     проверенный по отпечатку), `SITE_HOST`, `API_HOST` (те же, что в `.env` сервера); по желанию
     `DEPLOY_PORT` (22), `DEPLOY_PATH` (`/opt/mktba`), `METRIKA_ID`.
4. GitHub → Settings → Secrets and variables → Actions → Variables (уровень репозитория):
   `DEPLOY_STAGING_ENABLED=true` и/или `DEPLOY_PRODUCTION_ENABLED=true` — включают стенд.
5. Видимость пакетов `mktba-api` и `mktba-web` в GHCR менять не обязательно: сервер тянет их,
   войдя в реестр токеном джоба (он действует, пока идёт джоб, и после деплоя удаляется `docker logout`).

### Резервные копии (X-04)

Сервис `backup` в `deploy/docker-compose.yml` (образ `postgres:16-alpine`, тот же, что у базы, поэтому
`pg_dump` совпадает с сервером по версии) сохраняет базу и том `uploads`; логика — `deploy/backup.sh`.
Платных сервисов нет: копии лежат на диске сервера, копия на другую машину — по желанию.

| Когда | Метка | Сколько хранится |
| --- | --- | --- |
| по расписанию `BACKUP_SCHEDULE` (cron, UTC; по умолчанию `0 3 * * *`) | `scheduled` | последние `BACKUP_KEEP` (14) |
| `deploy.sh deploy` перед каждой миграцией (если в базе уже есть схема) | `pre-deploy` | последние `BACKUP_KEEP_PRE_DEPLOY` (5) |
| `deploy.sh backup` вручную | `manual` | пока не удалить руками |

Копия — каталог `BACKUP_HOST_DIR/<время UTC>-<метка>/` (по умолчанию `deploy/backups/`, на сервере
`/opt/mktba/backups/`, доступ только root): `mktba.dump` (`pg_dump -Fc`), `uploads.tar.gz`, `SHA256SUMS`.
Каталог пишется под временным именем и переименовывается, когда готов, поэтому каталог с итоговым
именем всегда целый. База снимается согласованным снимком; архив загрузок — сразу после неё, не в
той же транзакции (файл, загруженный в эти секунды, может оказаться без строки в базе или наоборот).
Ошибка копии перед миграцией останавливает деплой: api и web продолжают работать на старой версии.

```bash
cd /opt/mktba
./deploy.sh backup                       # копия сейчас
./deploy.sh backups                      # список
./deploy.sh verify                       # проверка восстановления самой новой копии (или verify <имя>)
./deploy.sh restore <имя> --yes          # вернуть копию: база и загрузки заменяются целиком
```

- **Проверка восстановления** (`verify`): сверяет контрольные суммы и читаемость архивов, восстанавливает
  дамп во временную базу `mktba_restore_check` рядом с настоящей, сверяет число таблиц с дампом,
  проверяет историю миграций и печатает число статей, пользователей и файлов; временная база удаляется.
  Её стоит запускать после настройки и потом время от времени (например, раз в месяц).
- **Восстановление** (`restore`): останавливает api и web, пересоздаёт базу из дампа, заменяет
  содержимое тома `uploads` архивом, затем прогоняет `migrate` текущей версии (копия могла быть
  снята до последних миграций) и запускает api и web. История деплоя не меняется.
- **Копия на другую машину** выключена, пока пуста `BACKUP_OFFSITE_COMMAND` в `deploy/.env`: это
  команда оболочки, которая выполняется в контейнере `backup` после каждой копии, `$1` — путь к ней.
  Значение — в одинарных кавычках. Нужные ей пакеты Alpine — `BACKUP_PACKAGES`, конфиг и ключи — в
  `deploy/backup-offsite/` (в контейнере `/offsite`, только чтение). Пример с rclone (другой сервер по
  SFTP, любое S3-совместимое хранилище) — в `deploy/.env.example`. Сбой копии пишется в лог
  (`docker compose logs backup`), локальная копия остаётся; `deploy.sh backup` в этом случае
  завершается с ошибкой.

CI (джоб `docker`, `scripts/test-backup.sh`) на временном стенде проверяет копию по расписанию и её
копию «на другую машину», `verify` на целой копии и его отказ на битой, `restore` после изменения
базы и загрузок и ротацию; `scripts/test-deploy.sh` — копию перед миграцией и запуск сервиса `backup`.

**Что нужно от владельца:** выбрать, куда уходит копия на другую машину (второй сервер, хранилище),
положить её конфиг в `deploy/backup-offsite/` и задать `BACKUP_PACKAGES` и `BACKUP_OFFSITE_COMMAND`
в `deploy/.env`; после первого деплоя запустить `./deploy.sh backup` и `./deploy.sh verify`. Без
копии на другую машину копии пропадут вместе с диском сервера.

### Наблюдаемость (X-05)

Всё работает без внешних сервисов; канал оповещений выключен, пока владелец его не настроит.

- **Логи.** API пишет в stdout JSON-строки (`Logging:Console:FormatterName=json`, время в UTC; в
  Development — обычный текст). На каждый запрос — одна строка: метод, шаблон маршрута (например
  `/articles/by-slug/{slug}/content`, а не сам адрес и не строка запроса), статус, время, `TraceId`
  (тот же, что в ответе с ошибкой). Ни IP, ни User-Agent, ни cookie, ни почты, ни токенов (решение D9).
  Запросы к `/health/*` не пишутся. Веб-сервер пишет ошибки загрузчиков и рендера JSON-строкой в stderr
  (метод и путь без строки запроса). Смотреть: `docker compose logs api web`.
- **Здоровье.** `GET /health/live` — процесс отвечает (всегда 200). `GET /health/ready` — база доступна
  и все миграции применены (иначе 503), плюс состояние фоновых задач: если последний прогон очистки
  загрузок, очистки черновиков, сборки статистики или доставки обратной связи упал или успешного прогона не было три
  интервала, статус `Degraded` (по-прежнему 200). Тело: `{ status, checks: { database, workers } }`,
  без текста исключений. В `deploy/docker-compose.yml` это healthcheck сервиса `api`
  (`dotnet Mktba.Api.dll --health-probe`: в образе нет curl), у `web` — запрос `/robots.txt`;
  `deploy.sh` ждёт обоих (`up --wait`), так что неготовый релиз не считается выкаченным.
- **Ошибки в браузере.** Скрипт сайта (`src/services/clientErrors.ts`, ~0,5 КБ) отправляет
  необработанные ошибки, отклонённые промисы и ошибки, пойманные границами ошибок, в
  `POST /client-errors`: сообщение, стек и путь страницы, не больше пяти за загрузку страницы, каждую
  один раз; выключен в разработке и в браузере под автоматизацией. API вычищает почту, строки запроса
  и токены и пишет отчёт в лог предупреждением категории `Mktba.ClientErrors`; в базу ничего не
  сохраняется. Ограничения: `RateLimiting:ClientErrors` (10 в минуту с адреса) и
  `ClientErrors:MaxPerMinute` (60 в минуту от всех, остальные принимаются и отбрасываются).
- **Оповещения.** Записи лога уровня `Alerts:MinimumLevel` (`Error`) и выше — необработанные 500,
  сбои фоновых задач — уходят в чат Telegram: одна запись одного вида раз в `Alerts:ThrottleMinutes`
  (30, повторы считаются и упоминаются в следующем сообщении), не больше `Alerts:MaxPerHour` (20) в
  час. Включается переменными `ALERT_TELEGRAM_BOT_TOKEN` и `ALERT_TELEGRAM_CHAT_ID` в `deploy/.env`
  (`ALERT_STAND` — имя стенда в сообщении). Токен не логируется.

**Что нужно от владельца:** создать бота у @BotFather, добавить его в свой чат и задать
`ALERT_TELEGRAM_BOT_TOKEN` и `ALERT_TELEGRAM_CHAT_ID` на стендах. Оповещения из самого API не
приходят, когда сервер лежит целиком, поэтому стоит завести внешний монитор доступности (например,
бесплатный UptimeRobot или свой Uptime Kuma) на `https://<API_HOST>/health/ready` и главную сайта.
